* PURPOSE
:PROPERTIES:
:TYPE: reference
:END:

Two instruments for the turtle runtime, built to diagnose *persistent high CPU*
and memory growth on low-compute clients (see [[file:../../../specs/turtle-rearchitecture.org]]
ALLOCATION DISCIPLINE). They split the pipeline at the WebGL boundary:

| Instrument | Covers                                  | Sees                                   |
|------------+-----------------------------------------+----------------------------------------|
| Headless   | parse → execute → scheduler (no THREE)  | allocation churn, retained references  |
| In-browser | render loop + compositor + materializer | RAF idle-spin, GPU object growth       |

The headless harness drains each ambient channel through a *counting stub* in
place of the materializer, isolating executor/scheduler cost from rendering.

* HEADLESS HARNESS
:PROPERTIES:
:TYPE: reference
:END:

#+BEGIN_SRC sh
node --expose-gc test/js/profile/run.mjs
node --expose-gc test/js/profile/typing_path_bench.mjs   # coreshell/CM keystroke spine
node --expose-gc test/js/profile/linter_bench.mjs        # CM decoration / tokenize
node test/js/profile/command_cost_bench.mjs             # cost spread across the command table
node test/js/profile/numeric_cost_bench.mjs             # the numerics units, per call
node test/js/profile/breath_cost_bench.mjs              # what the preemption boundary costs
node test/js/profile/frontend_bench.mjs                # reader · parser · lexer · evaluator
node test/js/profile/live_loop_bench.mjs               # the user loops, against a frame budget
node test/js/profile/point_read_bench.mjs              # scan · shared snapshot · prepared point pass
node --expose-gc test/js/profile/movement_latency_bench.mjs  # movement, against a frame budget
#+END_SRC

- =point_read_bench.mjs= rotates scanning/shared/prepared passes over real pinned-point worlds,
  includes preparation in timing, and counts snapshots/records separately. =POINTS= and =SAMPLES=
  configure it. Run alone; it measures model interpretation, not projection, DOM or GPU.
  Deterministic fences live in =test/js/laws/point_read_test.mjs=; [[id:runtime-prepared-point-read]].
- =harness.mjs= — =profileProgram(src, { ticks, frameMs })=: builds a real
  scheduler exactly as =turtle._ensureScheduler=, runs a batch flush then N
  animation ticks, brackets heap with =global.gc()=, walks the live frame tree
  for retained counts (=snapshotRetained=).
- =run.mjs= — representative suite + threshold asserts (regression guard; exits
  non-zero on a leak). Without =--expose-gc= it degrades to best-effort and
  skips heap assertions with a warning.
- =typing_path_bench.mjs= — reparse / contentKey / pageLaw.observe / findProse
  (spec memory: [[file:../../../specs/weave/typing-path.org][typing-path]]).
- =command_cost_bench.mjs= — ns/command across the whole =COMMANDS= table. The
  preemption quantum (D027 R3) is denominated in node visits, so it is only
  meaningful if a visit is roughly a visit: this reports the spread. It is what
  found =evaluateExpr= re-parsing on every evaluation (25x spread → 4x).
- =numeric_cost_bench.mjs= — ns/call for the numerics units (=conditionOf=, =demand=,
  =format= by value class) with =String= as a reference. Add it to the family because a
  whole COMMAND cannot resolve a unit: a 162 ns door inside a 3 000 ns command is inside
  the machine's resolution, and a CPU profile charges =yield*= delegation to the
  CALLER's self time, so neither instrument can see it. Multiply a unit by its calls per
  command to price a change.

** The estimator, and the noise floor it was chosen against
:PROPERTIES:
:TYPE: reference
:END:

Both command benches report *MIN of N* with each row's own *jitter* (=max/min=).
Measured 2026-10-02 on this machine: three same-tree runs of =command_cost_bench= spread
*1.3x–2.3x* per fixture, so the previous median-of-3 could not resolve a real change —
an A/B of a landed change read as ±30% of pure noise. GC inside the timed region is the
usual culprit and it only ever ADDS time, hence the minimum. MIN-of-5 brought the
same-tree spread to 1.1x–1.6x, which is tighter but still leaves *±10–15%* on a
whole-command A/B.

So: a whole-command delta under ~15% is not evidence. For a small change, use a unit
bench (deterministic per call), a CPU profile (attribution by self time), and the
*deterministic* allocation proxy — =node --trace-gc= scavenge counts over a fixed
workload, which is an integer and repeats to within ~1%.
- =breath_cost_bench.mjs= — what the breath costs, round-robin across quanta with
  an explicit noise gate, *and* worst-block-under-slice for the three B1 shapes.
  *It reports; it does not assert.* It began as asserting tests in
  =quantum_spike_test.mjs= and failed under load — a wall-clock ratio measures
  the machine. Correctness fences are deterministic and stay in =_test.mjs=
  (B1 keeps =deadlineChecks > 0= only); cost and worst-block are a bench.

*The leak signal* is =Δheap/tick= over the steady animation run: flat ≈ no leak.
=registry= / =frames= staying constant across re-execution ≈ no frame accumulation.

*Fixed while re-capturing*

- =command_cost_bench.mjs= used =count % 7=, which the lexer no longer accepts
  (=% / //= became =mod=), so the bench *crashed* instead of measuring. Now =[mod(count, 7) + 1]=.
- =evaluateExpr= built and ran two RegExp matches (quote, computed-dot) on *every*
  expression — including plain numbers. Guarded by first character and hoisted the
  patterns: ~89% less regex work per evaluation (measured in isolation; it was ~2% of
  executor time, below the end-to-end rig's noise).
- =parse.js= fence predicates (=isMeadowFence/isCellOpen/isCellClose=) ran a RegExp on *every*
  line, and =pushCode= ran a =\bend\b= replace on every line. A substring =includes= is a
  cheap superset (a fence line must contain its mark), so the RegExp now runs only when it can
  match. Measured: =parseProgram= 13 lines *22.1 → 10.9 µs* (2.0×); a 200k-parse loop with a
  =fn= + =label= *5683 → 1892 ms* (3.0×). Remaining top: =pushCode= (per-line allocations),
  =tokenizeLine= (char walk), =parseStatement=.

*Known cost accepted — and unguarded*

- =readArguments= (the shared command-argument reader) is *2.1×* the dumb split it replaced
  (13.0 vs 6.3 µs per held invocation): it lexes + parses where the old code split on
  whitespace. It runs on the *program-execution* path (a =let= figure declaration), not the
  animation path, so it stays bounded — but **the boundary reader has no bench in this rig**,
  which is the gap that let the change land unmeasured.

** Front-end and live-loop benches [2026-10-02]

Two benches for the FRONT of the user loop — the paths that run on every keystroke,
every flush, every expression. =frontend_bench.mjs= (reader · parser · lexer ·
evaluator) and =live_loop_bench.mjs= (keystroke · run · edit-live · held-figure,
each against the user's budget). Both guard only machine-independent ratios and
generous gross fences, so a busy machine cannot fail them.

*Front-end* (µs unless noted):

| path                          | cost        | note |
|-------------------------------+-------------+------|
| =readArguments= (1 held invocation) | *~1.1 µs* | ~9.5× the splitter it replaced — the cost of one contract |
| =parseProgram=                | 0.76 µs/line | flat across 4× size |
| =Lexer.tokenize= (=mod(count, 7) + 1=) | 1.42 µs | within 2× plain arithmetic |
| eval =round(x, n)=            | 1.66× =sin(1)= | builtins within 3× a stock builtin |

*Live loop* (fraction of the user's budget):

| loop                       | typical (p50) | budget        | floor   |
|----------------------------+---------------+---------------+---------|
| keystroke 8 cells          | 1.04 ms       | 6% of a frame | 0.89 ms |
| keystroke 40 cells         | 4.92 ms       | 30%           | 4.14 ms |
| keystroke 80 cells         | 9.88 ms       | *59%*         | 8.34 ms |
| run: first ink             | 0.62 ms       | instant       | —       |
| run: full flush (20k cmds) | ~25 ms        | batched — the breath preempts | — |
| edit-live (20-cell)        | ~1.1 ms       | 7%            | —       |
| 50 held figures            | ~0.45 ms      | 2.7% (reader share ~49%) | — |

Reads: the *keystroke* path is the reactivity ceiling — 80 cells ≈ 59% of a frame —
and it is **not GC** (measured 0.074 ms/keystroke = 0.8%, and =--max-semi-space-size=64=
did not move it; an earlier "GC-bound" read here was wrong, caused by a no-op edit
poisoning the floor with a fake-fast sample). It is *stable compute*: floor ≈ typical.

**The deeper lever [2026-10-02].** A CPU profile puts =contentKey= (=JSON.stringify= with
a replacer) at *~64%* of the keystroke path, and the reason is structural: the same
buffer is parsed **twice per edit** — the turtle runs =reparseProgram= (turtle.js:668)
and the weave seats with another =reparseProgram= (=asTree=, page.js:318), each with its
own held tree. Ablation at 80 cells:

#+BEGIN_EXAMPLE
reparse + contentKey + observe(doc: string)   8.77 ms   ← live path
reparse + contentKey + observe(doc: ast)      5.21 ms   ← −3.56 ms, −41%
reparse + observe(doc: string)                7.40 ms   (contentKey loop = 1.37 ms)
parseProgram + contentKey + observe(string)   5.88 ms   (adoption costs +2.9 ms over a plain parse)
#+END_EXAMPLE

=asTree= already accepts a pre-parsed tree (its =Array.isArray(doc)= branch); threading the
caller's tree through =observe= removes the second parse. Applied: the =contentKey= replacer
is now hoisted (stable identity — measured ~6%, free). The *reader* is ~49% of a
figure-heavy flush and ~10× the splitter — the price of one contract, now visible and
guarded so it cannot grow silently.

*CPU profile of the executor* (=--cpu-prof=, 100k× =fw/rt/label=, ~3.8k samples):
=walkBody= 35.6% self (the generator statement walk), =callCommand= 15.1% (a =ctx=
object plus a =[...position]= snapshot per command), GC 12.1%, =evaluateExpr= 8.7%.
The generator walk is the structural cost; the per-command allocations are the GC load.

  .then(m => m.attachProfilerOverlay(document.getElementById('core-canvas').__turtle))
// turtle.__profilerDetach() to remove

=overlay.js= wraps =turtle.onFrame= to count frames and samples on its own
=setInterval= (passive — never calls =requestRender()=, so observing does not
perturb). It reports:

- *Idle-spin verdict + idle fps* — frames doing a full =renderer.render()= while
  =scheduler.done= / no ambients and not recording. *This is the direct readout
  of the persistent-CPU root cause* (=render/loop.js= re-arms RAF unconditionally,
  =stopCondition: () => false=). A finished static drawing should idle at ~0 fps;
  today it spins at ~60.
- =renderer.info=: geometries, textures, draw calls, programs — climbing across
  redraws = the material-cache / geometry leak (cache is module-level, never
  pruned, and shared materials get =dispose()=d under it).
- =performance.memory= heap (Chrome), used/peak.
- Live counts: ambients (=registry.size - 1=), material-cache size.

** Baseline + fix verification [2026-05-29] — headless Chromium via chrome-devtools-mcp

Caveat: headless SwiftShader rAF is throttled (~10 fps here vs 60 on a real
foreground tab), so absolute render rates understate a real device ~6×. The
ratios and monotonic trends are valid.

*Cause #1 — RAF idle-spin.* After a finished batch program (=loop 200 do fw 5 rt 5 end=,
=scheduler.done=true=, camera untouched):

| Metric (idle window)        | Before          | After (render-on-demand) |
|-----------------------------+-----------------+--------------------------|
| renderer.render() calls     | 205 over ~19s   | *0 over 5s*              |
| overlay frames idle/total   | 758 / 758       | loop stopped             |
| RAF loop                    | running forever | *stopped*                |

Wake-on-demand verified: =requestRender()= → 1 frame then stop; camera
interaction → renders through the ~700ms damping settle window then stop;
animated program (=wait= → never done) → renders continuously, =done=false=.

*Cause #3 — material cache leak.* Redraw same buffer with distinct =bold N=
(thickness → distinct (color,thickness) key):

| Metric                      | Before     | After                         |
|-----------------------------+------------+-------------------------------|
| matCache after 12 redraws   | 12         | 12 (legit cache, 1 live path) |
| matCache after turtle.reset | 24 (stuck) | *0 (reclaimed)*               |
| post-reset redraw           | corruptable| clean (cache rebuilds from 0) |

Fixes: =clearMaterialCache()= on =compositor.dispose()=; compositor layer
teardown no longer disposes =_cached= shared materials (was use-after-dispose);
=updateMaterialResolution()= on resize. Within-session growth from slider churn
is still unbounded by design (legitimate cache; spec A3 assumes few combos) —
reclaimed on reset/navigate.

*Cause #4 — draw-call explosion (the real scaling wall).* =wait= returns
=stroke:"break"=, so an animated =loop do fw 1 wait end= emits one path event per
tick. The materializer made one persistent Line2 mesh per event → tens of
thousands of meshes/draw-calls for long animations. Observed on a pursuit-curve
program (8 mice × =loop 3600 ... wait=, + spinning parents):

| Metric         | Before   | After (trail consolidation)        |
|----------------+----------+------------------------------------|
| geometries     | 28,868   | *27*                               |
| draw calls     | 28,354   | *26* (≈ one per ambient, not tick) |
| heap (used)    | 261 MB   | *76 MB*                            |
| fps            | 6        | settles, then RAF stops            |

Fix: contiguous, same-(color,thickness) path events accumulate into ONE growing
Line2 per ambient (=accumulateTrail= / =flushTrail= in materializer.js, wired in
compositor =drainAndMaterialize=). A style change or discontinuity (jmp/pen-up)
starts a new run; filled polygons stay standalone; the run resets on clear.
Verified: =loop 400 ... wait= → 1 mesh (was 400); 8 mouse trails → 9 meshes;
re-spawn-in-loop → 2 meshes; renders identically (screenshot confirmed).

*Cause #5 — 60fps under heavy load (real-hardware, via attached Chrome).* After
#1–#4, a heavy animation held only ~39fps while the CPU sat 93% idle — so the
cap was not our work. Per-frame instrumentation (live browser) isolated two
throttles:

1. =compositor.advance= ran =drainAndMaterialize= INSIDE the catch-up tick loop,
   so =flushTrail= rebuilt every trail mesh ~34×/frame (32ms). Fix: tick the
   catch-up loop to fill channels, then drain + materialize ONCE per frame
   (channels accumulate across ticks). → advance 32ms → 4ms.
2. =render/loop.js= gated rendering on =deltaTime >= 1000/60=; RAF timestamps
   jitter just under 16.67ms on a 60Hz display, so frames were dropped (~40fps).
   Fix: render every RAF (already vsync-locked); render-on-demand still idles out.

| Program (sustained, real GPU) | fps before | fps after | draw calls |
|-------------------------------+------------+-----------+------------|
| single long trail             | 39         | *60*      | 1          |
| 8 mice (long)                 | ~40        | *60*      | 21         |
| 20 mice (long)                | —          | *60*      | 37         |

Per-frame after: onFrame 5.6ms (was 33ms) — headroom for 60fps. Idle still
0 renders / RAF stopped.

The in-browser baseline can be captured by an agent (no manual clicking) via the
=chrome-devtools= MCP server, registered local-scope for this project:

#+BEGIN_SRC sh
chrome-devtools-mcp --headless --isolated --executablePath /usr/bin/chromium \
  --experimentalMemory --chromeArg=--no-sandbox --chromeArg=--enable-unsafe-swiftshader
#+END_SRC

(=--enable-unsafe-swiftshader= is required for headless WebGL on Chromium 121+,
else the canvas =getContext('webgl2')= returns null. GPU/CPU absolute numbers are
software-rendered and not representative of a real device, but the *idle-spin*
and *renderer.info growth* signals are CPU-side counts and remain valid.)

Tools surface only after a Claude Code restart. Protocol per session:

1. =new_page= → navigate to =http://localhost:4000/shell?perf=1= (Phoenix already
   serves locally — a successful page load confirms it's up).
2. =evaluate_script= the probe (=__turtle= is exposed on the canvas):
   #+BEGIN_SRC js
   () => { const t = document.getElementById('core-canvas').__turtle; return {
     raf: t.renderLoop.state.animationFrameId != null,
     done: t.scheduler ? t.scheduler.done : null,
     ambients: t.scheduler ? t.scheduler.registry.size - 1 : 0,
     mem: t.stage.renderer.info.memory, calls: t.stage.renderer.info.render.calls,
     heapMB: performance.memory && +(performance.memory.usedJSHeapSize/1048576).toFixed(1) }; }
   #+END_SRC
3. *Idle-spin (cause #1):* type a batch program (=loop 200 do\n fw 5\n rt 5\nend=)
   via =evaluate_script= dispatching into the CM6 editor (or the LiveView render
   path), run =performance_start_trace= → wait 10s idle → =performance_stop_trace=.
   Verify RAF still firing + frames committed while =done=true= → idle CPU cost.
4. *Leak (cause #3):* snapshot =mem.geometries= + mat-cache, re-draw a
   color-varying program (=color [count]=) ~15×, re-snapshot. Growth that never
   recedes = the unbounded material cache.

* MOVEMENT LATENCY
:PROPERTIES:
:TYPE: reference
:END:

=movement_latency_bench.mjs= asks where movement costs what. It is a reading instrument:
each cell names its workload, records the outcome it observed, and reports the displacement
it achieved. A wish pattern is part of the fixture, not a detail.

The observed mechanism behind the expensive carry workload is recorded, without a ruling, at
[[id:laws-movement-cost-mechanism]] (=observed-laboratory=): near-tangent circle recomputation,
fixed-circle idempotence, non-monotone error over the bounded sweep, and the explicit
distinction between the loop's position-change test and the gate's acceptance tolerance. Carry
and follower rotation stay open there and here.

#+BEGIN_SRC sh
node --expose-gc test/js/profile/movement_latency_bench.mjs
ROTATE=7 RAW=/tmp/movement.jsonl node --expose-gc test/js/profile/movement_latency_bench.mjs
SAMPLES=50 ACTOR_EDITS=40 node --expose-gc test/js/profile/movement_latency_bench.mjs   # quick read
#+END_SRC

Scopes are named because they are not interchangeable:

| scope           | includes                                                                  |
|-----------------+---------------------------------------------------------------------------|
| =latency:hand=  | one =requestMotion= CALL only — the 2 settle ticks are excluded           |
| =settleMs=      | the 2 settle ticks, timed separately and reported as their own field       |
| =alloc:hand=    | warmed world; call + 2 settle ticks + drains, divided by operations        |
| =latency:motion=| one =scheduler.tick= whose observed attempt is =program-motion= and published |
| =alloc:motion=  | warmed world (3 observed motions outside); ticks carrying 20, per motion edit |

=RAW= is JSONL: the first line is schema metadata (version, runtime, source hash, scope
strings, sample counts); every row carries =phase ∈ {warm, measure, cold}=, =op=, =kind=,
=outcome=, =ms=, =delta=, =requested=, =before=, =after=, =displacement=, =command=, =path=,
and null slots for =members/reads/transforms= until the diagnostic pass fills them. Filter
=phase === "measure"= to reproduce the printed statistics. =warm= rows are retained and tagged;
=cold= means the FIRST operation in a FRESH world — never a process-cold claim. =ROTATE= changes
the timing order only.

*Diagnostic pass (M2).* After every timing cell, and never before one, the bench replays each
hand/unrelated cell's exact warmup and then, on the state the timing cell occupies, runs a
*replica* of one continuation call through a counting world, followed by one whole-door call
(the scheduler's own world wrapped and restored). Two witnesses bracket the replica:

1. *Identity*: every participant's frame, origin and transform objects are saved by reference
   and must be the same objects afterwards; every active law must keep its address, declaring
   frame and endpoints. Law OBJECTS cannot be witnessed this way — =laws.active()= materialises
   fresh records per call (measured), and the artifact records that fact rather than pretending
   otherwise.
2. *Value*: a digest over every participant's origin, local and world pose, membership and
   revision, and every law's address/feature/endpoints/owner/declaring frame, before and after.

Then the producer is compared against the door: the replica's candidate (writer + component) is
predicted in WORLD coordinates, the door is asked the same question on the same state, and the
bench asserts the door verdict's member set matches the candidate and that the installed world
poses equal the prediction within a declared 1e-12 diagnostic budget. Artifacts (=*.diag.jsonl=)
carry per cell: one-based ordinal, target, members (= writer + component), reads, transforms,
whole-door counts, signature match, and =maxPublishedPositionGap= /
=maxPublishedRotationGap=. In these identity-room fixtures both gaps are 0. For scale: at n=16
the rebasing cell's replica asks 253 reads / 46 transforms and re-places 2 members; the absolute
±2 cell asks 3157 / 541 and re-places 5–6. Those are counts of what the method asks for; they are
not an attribution and this file draws no conclusion from them.

What this instrument does NOT establish, and must not be read into it:

1. *No mechanism.* The continuation's sweep count, its convergence test and the gate's
   tolerance are being measured separately with an instrumented in-memory copy of the pinned
   module, not from these timings. A CSV of medians cannot attribute cost to a loop, and
   subtracting two cells does not either. No root-cause claim lives here until that
   instrument's equivalence checks (candidate output, effective published poses, source and
   copy hashes) land.
2. *No policy.* Refusal is not "no value" — a refused edit preserves obligations, and its cost
   (5.8 ms p50 to publish nothing) is a price of the search, not a verdict on it. A cheaper
   movement policy is not thereby the intended interaction. 16.67 ms is a whole frame, not a
   budget available to movement.
3. *No breadth.* GPUs/render, input scheduling, observers, competing work, continuous lawful
   trajectories, arbitrary constraint graphs, richer tower values entering geometry, other
   machines — all outside. Headless model time is not "what the user feels".
4. *No cold JIT claim.* The first motion tick is reported separately and labelled JIT; the
   =cold= phase is reserved for first operations in fresh worlds.
